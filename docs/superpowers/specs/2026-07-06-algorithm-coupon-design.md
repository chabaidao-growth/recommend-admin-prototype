# 推荐系统接算法发券 需求方案（Q3Q4）

> **状态：待评审 | 日期：2026-07-06 | 作者：何旭**
> 用途：与业务方、数仓/数据分析、营销中台、小程序前端对齐方向；评审通过后再产出 PRD 章节与后台原型页面。

---

## §0 结论摘要（TL;DR）

在小程序点单页新增**券位入口**，跳转现有**免费领取活动落地页**，落地页券列表做**千人千面排序**。因算法工程师已离职，Q3 上线**不依赖模型**，采用「**标签规则近似 uplift**」的降级策略（价格敏感度 × 购买活跃度四象限 + 品类/时段定向）；架构上把**分数源做成可插拔**，未来算法恢复后切回模型分，后台与推荐服务零改动。券资产全部由营销中台管理，推荐侧只做展示决策、无发券写操作。KPI 口径为**上线交付本身**，效果指标后置。

---

## §1 背景与目标

- **KPI**：Q3Q4 考核「算法发券链路上线交付」；领取率/核销率/ROI 等效果指标为后续迭代目标，本期不考核，不建 AB 实验基建。
- **核心约束**：算法工程师已离职，目前无算法人力。历史上曾共建两个模型（2025-04）：
  - **uplift 模型**：对每个用户输出发券增量价值分；
  - **购买率预估模型**：对每个用户输出购买概率分。
  - 两者距今 15 个月无人维护。判断：**无人维护的模型是负债不是资产**——分布漂移无人评估、特征管道断裂无人排障，且是「看起来还在跑」的静默失效风险。故不进入 Q3 交付链路（处置方案见 §4.7）。
- **设计原则**：如无必要，勿增实体。复用现有系统能力（营销中台券体系、免费领取落地页、数仓标签、本后台交互范式），新建的只有「券候选池 → 券投放策略 → 场景绑定」一条配置链路和一张标签表。

## §2 业务链路

```
小程序点单页 券位入口（楼层）
    → 跳转 免费领取活动落地页
    → 落地页券列表按推荐接口返回顺序渲染（千人千面）
    → 用户点击领取（营销中台现有领券接口，链路不动）
    → 下单核销（营销中台现有核销链路，不动）
```

- 推荐侧职责边界：**只决定「谁看到哪些券、什么顺序」**，无发券写操作，天然幂等、无资金安全面。
- 券位入口本身展示什么（静态楼层图 vs 露出第一张券）为待确认项，见 §10。

## §3 系统边界与分工

| 系统 | 职责 | 改动量 |
|---|---|---|
| 营销中台 | 建券、券模板、库存、预算、领取接口、核销 | **零改动** |
| 数仓 | T+1 产出用户标签表（人群分层 + 品类/时段偏好） | 新增 1 个 T+1 任务 |
| 推荐服务 | 出券接口：标签表 + 后台配置 → 该用户的排序券列表 | 新增接口 |
| 本后台 | 券候选池 / 券投放策略 / 场景绑定 的配置管理 | 新增模块（§5） |
| 小程序 | 点单页券位入口；落地页按接口顺序渲染 | 落地页改造（外部依赖，§8） |

## §4 个性化策略（核心章节）

### 4.1 分数源可插拔架构

策略层只依赖一张**接口形态固定**的 T+1 表：

```
user_id → 人群分层编码 / 品类偏好 / 时段偏好 / 数据日期
```

- **Q3**：分层来源优先直接引用 **CDP 现有人群圈选能力**（2026-07-06 盘点确认可行，见 §4.7），数仓 SQL 产出 T+1 标签表降级为备选路径；
- **未来**：算法人力恢复后，翻新 uplift/购买率模型输出**同一形态**的表，直接切换数据源，后台配置与推荐服务零改动。

这条设计使 KPI 交付不被算法人力卡死，且为模型回归预留了无缝升级路径。

### 4.2 标准档：双标签近似 uplift 四象限

沿用已验证过的 uplift 框架思想，用**价格敏感度 × 购买活跃度**两个标签交叉近似四象限：

| | 高价格敏感（领券率高、核销率高、有券才买） | 低价格敏感（无券也照买） |
|---|---|---|
| **活跃**（近 30 天有购买，F 高） | 低门槛小面额券，促频次 | ≈ Sure things：**不发或仅新品尝鲜券**，节省预算 |
| **衰退**（R 30–60 天，F 下滑） | ≈ **Persuadables：主力发券人群**，中高面额挽留券 | 非价格型权益试探（新品券/加料券） |
| **流失**（>60 天未购） | 高面额召回券，小成本试探 | ≈ Lost causes：低优先级，仅兜底通用券 |

标签取数口径（2026-07-06 盘点后更新，两个维度均为 CDP 现成标签，见 §4.7）：

- **价格敏感度**：优先直接用 CDP「**价格敏感人群**」标签；备选为用「优惠券使用/领券未核销/促销活动参与」等标签组合自建口径（近 180 天领券核销占比思路）；
- **购买活跃度**：CDP「RFM（新）」「生命周期」「活跃度」标签直接引用。

> ⚠️ 「价格敏感人群」等标签的加工口径与数据准确性仍需与 CDP/数仓确认（用券数据「有但不一定准」），盘点结论决定采用标准档还是降级档。

### 4.3 降级档：仅 RFM 生命周期分层

若用券行为数据经盘点不可用：放弃价格敏感度维度，仅用已有 RFM 标签做生命周期分层（新客 / 成长 / 成熟 / 衰退 / 流失），每层映射一个券包。个性化粒度粗一档，但零数据风险、零新增数仓依赖，仍满足「个性化发券上线」的 KPI 口径。

### 4.4 定向维度（决定「发哪张」，而非「发不发」）

以下均为 CDP 已有标签（见 §4.7 全量目录）：

- **品类/口味偏好**：新品偏好、系列偏好、甜度/温度/杯型/小料偏好、预测奶茶/咖啡喜好度 → 券定向到对应品类或新品；
- **时段偏好**：习惯下单时间-时段/星期、作息时间偏好 → 匹配券的可用时段。

### 4.5 兜底规则

- 无标签用户（新客、数据缺失、标签表当日未产出）→ **默认券包**：运营在后台配置的固定顺序通用券列表；
- 兜底不为空是硬约束：落地页任何情况下都有券可展示（除非候选池本身为空）；
- **合规**：命中 CDP「拒绝个性化推荐」标签的用户，一律走默认券包，不做千人千面；
- **风控**：「活动羊毛党」「异常羊毛党用户」「风险用户」等标签人群，按运营配置排除发券或仅进兜底通用券（发券场景对羊毛党敏感，此项建议 Q3 即上）。

### 4.6 人群 → 券包映射

运营在后台按「人群分层 → 券包（候选池内券的子集）+ 排序优先级」配置映射规则；同一人群命中多规则时按优先级取首个。具体人群阈值（R/F 切分点）与券包内容由运营结合数据分析确定，不在本方案硬编码。

### 4.7 CDP 标签盘点结果（2026-07-06）

盘点来源有二：① CDP 人群 MCP（测试环境）实测，确认了建人群 JSON 格式与 7 个标签的参数规格（见附录 B）；② `cdp-audience` 圈人技能（`/Users/hexu/业务闭环/skills/cdp-audience`）内的**全量标签目录（312 个）**与圈人业务规则。方案所需标签全部有现成货：

| 用途 | CDP 已有标签（中文名） |
|---|---|
| 人群分层（发不发） | RFM / RFM（新）/ R/F/M 单值、4A分层 / 4A分层(新)、生命周期、活跃度、预估流失、年度复购状态、用户价值分组、购买力、茶百道策略人群 |
| 价格敏感（发多大） | **价格敏感人群**（直接可用）、优惠券使用、用户优惠券数量、领券未核销、价格偏好、单均价范围、促销活动参与、团购偏好 |
| 品类/口味定向（发哪张） | 新品偏好、系列偏好、甜度/温度/杯型/小料偏好、预测奶茶/高端奶茶/高端咖啡喜好度 |
| 时段定向 | 习惯下单时间-时段/星期、作息时间偏好 |
| 行为细分 | 未消费天数、复购次数、30天内复购频次、订单量、首单后沉默、注册不下单、首购距今天数 |
| 合规/风控排除 | **拒绝个性化推荐**、活动羊毛党、异常羊毛党用户、风险用户、异常下单用户、白名单用户 |
| **疑似旧模型输出** | **营销敏感度排名 / 营销敏感度排名头部百分比**（疑似 uplift 模型输出）、**预估下单率排名 / 预估下单率排名头部百分比**（疑似购买率预估模型输出）、营销算法分层 |

对方案的修正：

1. **标准档直接落地**：「价格敏感人群 × RFM/生命周期」交叉近似 uplift 四象限，两个维度都是现成标签，不需要任何新建数据任务；
2. **Q3 实现路径简化**：人群圈选直接用 CDP 现有人群能力（标签 and/or/diff 组合 + 人群嵌套引用），本后台「人群 → 券包映射」中的人群**引用 CDP 人群 ID**（与券引用营销中台同构）；「数仓 T+1 标签表」降级为备选路径；
3. **重大待确认**：「营销敏感度排名」「预估下单率排名」很可能就是离职算法工程师两个模型（uplift / 购买率预估）当年落到 CDP 的输出标签。**若其产出管道仍在更新，则「模型分」已有现成插槽数据，标准档可直接升级**；若已停更（大概率停留在 2025-04），则确认后从可用清单剔除——此项是 §10 最高优先级待确认问题之一；
4. 圈人业务规则沿用 cdp-audience 技能沉淀：历史未购用 4A分层=O、X 天内无购买用「排除 X 天内订单量≥1」、地域优先「常购省市」等。

**限制**：人群列表查询接口需用户登录态（MCP token 仅过网关），推荐服务生产化时需解决服务身份授权；中文标签名 → 系统内部标签名（如 会员等级 ↔ `member_level`）的映射与各标签参数规格，通过 cdp-audience 的 draft_hub `/api/labels` 接口或 CDP 团队获取。

### 4.8 旧模型处置

不进 Q3 交付链路，不删除。附验证清单，作为 Q4 可选增强项评估：

1. 打分管道是否仍在产出 T+1 分数表；
2. 分数分布相对 2025-04 基线漂移程度（分位数对比）；
3. 特征依赖的数仓上游表是否仍在维护、结构是否变更；
4. 若以上通过，可将模型分作为 §4.1 插槽的一路分数源灰度对比标签版。

## §5 后台配置能力（平行券链路）

新建与商品推荐链路**平行同构**的券链路，不改动商品链路任何已 QA 确认口径：

```
券候选池（引用营销中台券 ID）
    → 券投放策略（人群→券包映射 + 优先级 + 兜底顺序）
    → 场景绑定（Q3 仅一个场景：免费领取活动落地页）
```

- **券候选池**：从营销中台同步/检索券，按 ID 引用加入池内；池内维护券的启停；券模板变更、库存、有效期均以营销中台为准，本后台只读展示。
- **券投放策略**：§4 的人群→券包映射规则 + 兜底券包配置。
- **场景绑定**：场景 ← 策略的绑定关系；Q3 单场景，Q4 可扩展多场景。
- **状态依赖与删除口径**：完整复用现有 PRD §2.3——停用自顶向下、启用自底向上、删除须先停用、被引用对象停用/删除后下游保留原名称 +「已停用/已删除」标识、保存/启用时重新校验。
- 与既有导航的关系：落入「候选层 → 优惠券候选池」占位 + 新增券策略/场景绑定入口（信息架构细节在 PRD 阶段定）。

**已否决的备选方案**：
- 泛化四层架构（商品/券统一抽象为物料）：需重审 v3.8 已 QA 确认的全部商品特化口径，Q3 无法交付，否决；
- 极简单页场景配置：最快上线但 Q4 多场景/多策略扩展时需重构，作为进度风险时的降级备选。

## §6 接口契约

1. **数仓 → 推荐服务**：T+1 标签表
   `user_id, 人群分层编码, 品类偏好, 时段偏好, 数据日期`
2. **推荐服务 → 落地页**：出券接口
   - 入参：`user_id`（必填）、`门店 ID`（预留）；
   - 返回：排序后的 `[券ID, 排序来源标识（策略命中/兜底）]` 列表；
   - 券的实时库存、已领取状态、领取动作均由落地页调营销中台现有接口处理，推荐侧不感知；
   - 异常兜底：标签缺失走默认券包；推荐接口不可用时落地页降级为现状展示逻辑（不阻断领券）。

## §7 埋点与监控（轻量）

- 漏斗：券位曝光 → 落地页 PV → 券曝光 → 领取 →（T+1）核销；

- 本期不建 AB 实验基建（KPI 为交付本身）。

## §10 待确认问题

1. **「营销敏感度排名」「预估下单率排名」「营销算法分层」标签的产出来源与更新状态**——疑似离职算法工程师两个模型（uplift/购买率预估）的输出（§4.7）：若仍在 T+1 更新则模型分直接可用（标准档升级），若停更（大概率 2025-04 后）则剔除。找数仓/CDP 团队确认产出任务归属；

## 附录 B：CDP 人群 MCP 标签使用方式（2026-07-06 实测）

**接入**（测试环境）：
- Streamable HTTP：`https://ai-gateway-qa.shuxinyc.com/mcp-servers/bigdata-cdp-mcp-test-new`
- SSE：同路径 + `/sse`
- 鉴权 Header：`X-Mcp-Token`（token 走内部渠道获取）；注意该 token 仅过网关，`cdp_user_group_list` 等业务接口另需用户登录态

**工具**：`cdp_user_group_list`（查人群列表，需登录态）、`parse`（建人群参数校验，校验通过返回前端 JSON 含 labelId/中文名等元数据）、`reverse_parse`（前端 JSON 转逻辑 JSON）

**建人群逻辑 JSON 格式**（parse 入参，实测得出）：

```json
{
  "condition_groups_relation": "and | or",
  "condition_groups": [
    {
      "condition_type": "label | group",
      "condition_relation": "and | or",
      "conditions": [
        { "label_name": "rfm_type",
          "parameters": { "operator": "in", "values": ["重要挽留客户"] } },
        { "label_name": "coupon",
          "parameters": { "operator": "in", "type": "优惠券类型",
                           "values": ["代金券"], "recent_days": 90, "used": true } },
        { "label_name": "total_amount",
          "parameters": { "operator": "in", "values": [],
                           "start": 0.01, "end": 100,
                           "is_dynamic_date": true, "dynamic_recent_days": 30 } }
      ]
    },
    { "condition_type": "group", "condition_relation": "and",
      "conditions": [ { "group_id": "<已有人群ID>" } ] }
  ]
}
```

- ENUM 型标签：`operator + values`（values 必须命中值域，否则报 INVALID_ENUM_VALUE 并返回候选值）；
- 数值区间型：`start`（≥0.01）+ `end`，支持 `is_dynamic_date + dynamic_recent_days` 动态时间窗；
- 行为型（coupon）：`type`（优惠券类型/模板ID/名称/渠道）+ `values` + `recent_days` + `used`；
- `condition_type=group`：以 `group_id` 嵌套引用已有人群；
- 品牌 ID：茶百道 = 367430（parse 返回的前端 JSON 中确认）。
